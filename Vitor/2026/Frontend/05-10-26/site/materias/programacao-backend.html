Questão 10

"HTTP é um protocolo cliente-servidor no qual o cliente envia uma requisição composta por método, URI e cabeçalhos, e o servidor processa essa solicitação retornando uma mensagem de resposta com um código de status e o recurso solicitado."

Fonte: https://developer.mozilla.org/pt-BR/docs/Web/HTTP/Guides/Overview/html.

Durante os testes de homologação de um sistema de gerenciamento de entregas, diversos dispositivos enviam solicitações ao servidor simultaneamente. A análise do fluxo HTTP é necessária para compreender a sequência de comunicação e identificar possíveis pontos de atraso no processamento das solicitações. Considerando a arquitetura cliente-servidor e o protocolo HTTP descritos no texto, analise a situação e assinale a alternativa que representa a sequência correta do fluxo básico de processamento da comunicação.

  1. O cliente envia a requisição HTTP, o servidor processa a solicitação e o servidor envia a resposta com o código de status.
  2. O servidor envia a resposta inicial, o cliente processa a solicitação e o servidor confirma o recebimento da mensagem.
  3. O servidor processa o recurso local, o cliente envia a requisição de confirmação e o servidor recebe o código de status.
  4. O cliente recebe a resposta da aplicação, o servidor envia a requisição de validação e o cliente processa o recurso final.
  5. O servidor recebe a resposta do cliente, o cliente processa o recurso requisitado e o servidor envia a requisição de encerramento.
Ver resolução

Alternativa correta: A. O ciclo fundamental do protocolo HTTP é estritamente baseado no padrão requisição-resposta iniciado pelo cliente: o cliente envia a mensagem com o método e cabeçalhos, o servidor recebe, executa o processamento interno e devolve uma resposta com o código de estado (status code) e o corpo de dados.

Porquê: em HTTP quem inicia é sempre o cliente; as demais alternativas invertem a ordem (servidor respondendo antes de receber).

Questão 11

"Falhas no registro de logs e no monitoramento permitem que ataques passem despercebidos. As APIs devem garantir o registro de eventos de segurança, tais como falhas de autenticação e erros de validação, integrando os logs a sistemas de monitoramento contínuo para detecção de comportamentos anômalos."

Fonte: https://owasp.org/API-Security/editions/2019/pt-BR/0xaa-insufficient-logging-monitoring/.

Em uma infraestrutura de microsserviços, foram observados picos repentinos no tempo de resposta das requisições e aumento não previsto na taxa de erro 500 em endpoints críticos. A análise centralizada dos registros e a checagem das métricas foram definidas como prioridade para diagnóstico técnico. Com base nas recomendações da OWASP e na situação descrita, analise as condutas apresentadas e assinale a alternativa que especifica a estratégia correta para identificar a origem dos problemas de desempenho e segurança na API.

  1. Monitorar exclusivamente os indicadores financeiros de conversão, reduzindo o volume de armazenamento dos logs de erro do servidor.
  2. Monitorar continuamente os eventos técnicos da API, centralizar os registros de auditoria e configurar alertas automatizados para comportamentos anômalos.
  3. Analisar de forma isolada as métricas de espaço em disco no banco de dados, ignorando a taxa de rejeição nas autenticações de usuário.
  4. Acompanhar apenas a documentação cadastral das rotas, suspendendo a geração de registros de log para otimizar o tempo de resposta.
  5. Registrar apenas as requisições que retornam status de sucesso, descartando registros de erros de validação e falhas de autenticação.
Ver resolução

Alternativa correta: B. A diretriz de segurança da OWASP recomenda centralizar logs e métricas de sistema, acompanhando erros técnicos e acionando alertas quando surgem padrões anormais de tráfego ou respostas HTTP 500 repetidas.

Porquê: sem log de erro e sem monitoramento contínuo, ataques e falhas passam despercebidos — as demais alternativas reduzem ou desligam justamente o que permite diagnosticar.

Questão 13

O OWASP ZAP (Zed Attack Proxy) permite realizar testes de segurança dinâmicos (DAST) em aplicações web e APIs. Por meio da funcionalidade de importação de definições OpenAPI, a ferramenta pode executar verificações automatizadas nos endpoints mapeados para identificar vulnerabilidades, como falhas de injeção e problemas de controle de acesso.

Fonte: https://www.zaproxy.org/docs/docker/api-scan/.

Antes da liberação em ambiente de produção de uma nova API RESTful de pagamentos, exige-se a realização de testes de segurança automatizados do tipo DAST (Dynamic Application Security Testing) para validar os endpoints expostos contra vulnerabilidades conhecidas da OWASP. Considerando o cenário apresentado e as especificações das ferramentas de teste, analise as opções e assinale a alternativa que indica a ferramenta adequada e a justificativa correta para a realização dessa validação.

  1. OWASP ZAP, pois realiza testes dinâmicos automatizados varrendo os endpoints mapeados na documentação da API em busca de vulnerabilidades em tempo de execução.
  2. Snyk, pois atua como proxy reverso para interceptar conexões de rede e criptografar o tráfego de dados entre o cliente e o servidor.
  3. Gulp, pois automatiza o processo de compilação do código e substitui as validações de segurança dos dados recebidos pelos endpoints.
  4. Nmap, pois analisa o código-fonte estático para identificar bibliotecas desatualizadas e falhas de sintaxe na linguagem de programação.
  5. Postman, pois compila automaticamente os componentes da infraestrutura e elimina as falhas de injeção diretamente no banco de dados.
Ver resolução

Alternativa correta: A. O OWASP ZAP atua como scanner DAST enviando requisições contra os endpoints ativos do sistema para detectar falhas em tempo de execução, usando esquemas OpenAPI como guia de rotas.

Porquê: as demais ferramentas têm outro papel (Gulp = build, Nmap = rede/portas, Postman = cliente HTTP) e nenhuma faz varredura DAST guiada por OpenAPI.
